# Parallel work brief: MCP payload budget and field semantics

**Audience:** an agent working in parallel with the MCP read-path lane. Self-contained
— you are not expected to have context from the other lane. Read it all before writing code.

**Scope:** standing-brief items §6.4 (payload size) and §6.5 (field-semantics collision).
Nothing else.

---

## 1. What Avala is, in one paragraph

Avala runs data infrastructure for Physical AI: data collection, sensor fusion,
auto-labeling, human-in-the-loop annotation, 4D Gaussian Splatting reconstruction.
Customers are autonomous-vehicle and robotics companies (Lucid, Serve, Torc, Physical
Intelligence). A large distributed annotation workforce, concentrated in Kenya, does the
human work. The MCP server is how AI agents read Avala state. The measure of its quality
is not endpoint coverage — it is whether an agent with no other context can complete a
realistic job using only these tools.

## 2. Where the code is

`sdks/typescript/packages/mcp-server/` in the `avala-ai/avala` monorepo. TypeScript, run
with `bun`, tested with `vitest`.

- `src/catalog.ts` — the declarative tool registrar. 36 of 64 tools register through
  `registerReadCatalogTool`, which builds path + query from a route definition, validates
  against an `outputSchema`, sanitizes, and returns both `structuredContent` and text.
- `src/tools/*.ts` — per-domain tool definitions. 28 tools are hand-written
  `server.registerTool` calls that bypass the catalog.
- `docs/tool-inventory.md` — generated by `bun scripts/tool-inventory.ts`. Regenerate it
  as part of your change; it is a committed artifact and must not go stale.

Read `docs/phase0-baseline.md` first. It is short and it explains the shape of the surface
you are about to change.

## 3. Your two defects

### 3.1 §6.5 — one field name, two meanings (do this first; it is smaller and it unblocks 3.2)

`list_datasets` reports `itemCount: 39` for the `sf-lidar` dataset. `get_dataset_health`
reports `itemCount: 3120` **and** `sequenceCount: 39` for the same dataset. One counts
sequences, the other counts frames, under an identical field name. Confirmed in
`src/tools/datasets.ts`: `itemCount` at line ~15, and `itemCount` beside `sequenceCount`
at lines ~81–82.

Any agent reasoning across both tools produces wrong numbers, and so does any human
reading two screens.

**Required:**

- Rename to unambiguous names: `sequenceCount`, `frameCount`, `assetCount`. Pick per
  field based on what it actually counts — **verify against the upstream response, do not
  infer from the name.**
- **Keep the old key as a deprecated alias for one release.** Both keys present, same
  value, with the deprecation stated in the field description. Do not break existing
  clients; that is a hard rule in this repo.
- **State the unit in every field description.** "Number of sequences (recording runs) in
  this dataset", not "count".
- Where a rename crosses into `packages/sdk`, mirror it there and note it in the PR.

### 3.2 §6.4 — payloads make multi-step work impossible

A single `list_datasets` with `limit: 10` returns full `predefinedLabels` arrays of
forty-plus label objects per dataset, complete nested project lists, featured item URLs,
and signed logo URLs. It consumes a large fraction of a context window in one call. An
agent cannot chain three of those, which means it cannot do multi-hop work, which is the
entire point of the surface.

**Required:**

- **A `detail` parameter on every list and get tool, defaulting to `concise`.** Concise is
  roughly: `uid`, `name`, `slug`, `dataType`, the corrected count fields from 3.1,
  `status`, `owner`, `updatedAt`. Labels, nested projects, and media move to
  `detail: "full"` or to dedicated tools.
- **Cursor pagination on every list tool**, exposing `has_more`, `next_cursor`, and
  `total_count` where it is cheap to obtain. Default limit 20–50.
- **Server-side filtering.** Fetching everything and trimming client-side works at 500
  daily active coworkers and dies at 15,000. If an upstream route cannot filter
  server-side, say so in the PR rather than emulating it in the client.
- **A test asserting no default-detail list response exceeds 8,000 tokens.** Count tokens
  with the Anthropic SDK's `countTokens`, never a character heuristic and never
  `tiktoken`. A budget without a test is a wish.

Targets this serves, from the standing brief: max single response < 8,000 tokens; p95
tool-response tokens per task < 25,000.

## 5. Repo conventions you must follow

- **Work in your own git worktree**, branched from `origin/develop`. Do not switch
  branches in the main checkout — other agents are working there.
  `git worktree add ../avala-payload -b feat/mcp-payload-budget origin/develop`
- **Never `git stash` in a worktree.** `refs/stash` is shared across every worktree of
  this clone, so a `pop` can apply — and then drop — another agent's work. This has
  actually happened here. Commit WIP instead.
- **Build the SDK before running mcp-server tests** (`packages/sdk` must have a `dist/`),
  or you will get confusing module-resolution errors in a fresh worktree.
- **Verification, in this order, before you open the PR:** `npx tsc --noEmit` (must be 0
  errors — note that `vitest` transpiles without typechecking, so passing tests do NOT
  prove it compiles), then `npx vitest run` (currently 305 passing; do not reduce that
  number), then regenerate `docs/tool-inventory.md`.
- **The PR body MUST contain a `## Knowledge encoded` section** naming the rule, test, or
  doc you added — a CI guard fails the PR without it. `none` plus one line is acceptable
  only if nothing was learnable.
- **Add the `don't merge` label via REST and read it back.** `gh pr edit --add-label`
  fails *silently* on this repo:
  `gh api --method POST repos/avala-ai/avala/issues/<PR#>/labels -f "labels[]=don't merge"`
  then `gh api repos/avala-ai/avala/issues/<PR#>/labels --jq '.[].name'`
- The GitHub Codex review bot is out of quota, so **no automated review will run.** Your
  own verification is the only gate. Say plainly in the PR what you did and did not test.

## 6. Traps this codebase has already sprung on people

These are not hypothetical. Each cost real time in the last two days.

- **Do not count anything in a structured file with `grep`.** Four separate checks
  returned confident, specific, wrong integers because each ran over the wrong substrate —
  a grep counted schema documentation in header comments as data; one file greped as
  containing 2 of an element it had **zero** of. Parse; walk the nodes. The full write-up
  is `.claude/rules/ci-green-means-tested.md` §7.
- **A test must not assert that a defect persists.** If you find a bug and pin it with
  `assert(broken_thing_is_still_broken)`, the test goes red the moment someone fixes it,
  making a good change look like a regression. Assert the invariant you want instead.
- **A green test run is not evidence anything ran.** Check a test count, or a per-test
  line count, before believing a pass. Read `.claude/rules/ci-green-means-tested.md`.
- **Every field is a decision.** Do not keep a field in a `concise` response because it
  was already in the upstream payload. That reasoning is what produced the current
  payloads.

2. `detail` on every list and get tool, defaulting to `concise`.
3. Cursor pagination with `has_more` / `next_cursor` / `total_count`.

5. A regenerated `docs/tool-inventory.md`.
6. `tsc --noEmit` clean, `vitest` at 305 or more passing.
7. A PR body stating what you measured, what you could not, and any field you deliberately

one described optimistically — the next lane's decisions depend on your account being
true, and an overstated "done" here poisons a measurement suite that three agents just
spent a day making trustworthy.
